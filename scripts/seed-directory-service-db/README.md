# Заполнение базы DirectoryService

Go-утилита генерирует тестовые подразделения, должности, локации и связи между ними, затем записывает их напрямую в PostgreSQL. Подходит для подготовки локальной базы к ручной проверке интерфейса и запросов.

Скрипт не вызывает API DirectoryService, не проверяет доменные правила и не обновляет кеш сервиса. Используйте отдельную базу для разработки, предпочтительно до начала работы приложения с данными.

## Требования

- Go 1.27.0 или совместимая более новая версия — см. [go.mod](go.mod).
- Доступная база PostgreSQL с применёнными миграциями DirectoryService и пользователем с правами записи.
- Доступ к зависимостям Go при первом запуске.

Подготовка окружения и применение миграций через Compose описаны в [корневом README](../../README.md). Утилита сама не создаёт базу, таблицы или расширения PostgreSQL.

## Настройка

Выполняйте команды из `scripts/seed-directory-service-db`:

```bash
cp .env.example .env
```

Заполните `.env` по [образцу](.env.example). Файл загружается из текущего рабочего каталога и обязателен даже при передаче всех настроек через переменные окружения. Уже заданные переменные окружения имеют приоритет над значениями файла.

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_HOST` | Хост PostgreSQL; при запуске с компьютера для Compose — `localhost` |
| `POSTGRES_PORT` | Опубликованный порт PostgreSQL из корневого `.env` |
| `POSTGRES_USER` | Пользователь базы DirectoryService, соответствует `DIRECTORY_POSTGRES_USER` в Compose |
| `POSTGRES_PASSWORD` | Его пароль, соответствует `DIRECTORY_POSTGRES_PASSWORD` |
| `POSTGRES_DB` | База DirectoryService, соответствует `DIRECTORY_POSTGRES_DB` |
| `DEPARTMENTS_COUNT` | Верхний индекс генерируемого подразделения; особенность количества описана ниже |
| `DEPARTMENTS_ROOT_MIN_COUNT` | Минимальное число корневых подразделений включительно |
| `DEPARTMENTS_ROOT_MAX_COUNT` | Максимальное число корневых подразделений включительно |
| `POSITIONS_COUNT` | Количество должностей |
| `LOCATIONS_COUNT` | Количество локаций |
| `DEPARTMENTS_POSITIONS_COUNT` | Желаемое количество уникальных пар «подразделение — должность» |
| `DEPARTMENTS_LOCATIONS_COUNT` | Желаемое количество уникальных пар «подразделение — локация» |

Имена переменных пользователя и базы здесь отличаются от корневого `.env`: копирование административных настроек PostgreSQL из него может подключить скрипт к другой базе.

Строка подключения собирается как PostgreSQL URI. Специальные символы в имени пользователя и пароле должны быть корректно закодированы для URI. Не добавляйте реальные пароли в репозиторий.

### Параметры генерации

Задавайте целые неотрицательные числа. Ошибки преобразования чисел не обрабатываются: пустая или некорректная строка превращается в `0`.

Для дерева подразделений выбирайте значения:

```text
1 <= DEPARTMENTS_ROOT_MIN_COUNT <= DEPARTMENTS_ROOT_MAX_COUNT <= DEPARTMENTS_COUNT
```

В текущей реализации цикл добавления дочерних подразделений включает верхнюю границу. При этих условиях `DEPARTMENTS_COUNT=100` создаёт **101 подразделение**, включая корневые. Нулевые значения из `.env.example` не являются рабочим сценарием: генератор пытается выбрать родителя из пустого списка и завершается с panic. Если минимальное и максимальное число корней переставлены местами, генератор меняет их местами автоматически.

Количество связей ограничивается числом возможных пар: произведением количества подразделений и количества должностей или локаций. Пары не повторяются в пределах одной генерации. Все связи с локациями получают `is_primary=false`.

Например, для небольшой базы:

```dotenv
DEPARTMENTS_COUNT=100
DEPARTMENTS_ROOT_MIN_COUNT=3
DEPARTMENTS_ROOT_MAX_COUNT=5
POSITIONS_COUNT=20
LOCATIONS_COUNT=10
DEPARTMENTS_POSITIONS_COUNT=100
DEPARTMENTS_LOCATIONS_COUNT=50
```

Родитель каждого дочернего подразделения выбирается случайно среди уже созданных. UUID, адреса и названия должностей и локаций также генерируются заново. Фиксированного seed для воспроизводимого набора данных нет.

## Запуск

После настройки подключения и применения миграций:

```bash
go run .
```

Утилита подключается к базе, генерирует данные в памяти и последовательно вставляет их в таблицы `departments`, `positions`, `locations`, `department_positions` и `department_locations`. Для вставок открывается одна транзакция; в консоль выводятся результаты отдельных SQL-команд.

При повторном запуске выполняются новые `INSERT`: очистки таблиц, обновления существующих записей и режима upsert нет. Имена и slug подразделений снова начинаются с `Department 0` и `department-0`. Возможны дублирующиеся названия и конфликты ограничений; для нового независимого набора используйте подготовленную пустую базу.

## Совместимость и ограничения

- SQL находится в [database.go](database.go) и соответствует текущим именам таблиц и столбцов в [конфигурациях EF Core](../../backend/DirectoryService/src/DirectoryService.Infrastructure.Postgres/Configurations/). При изменении схемы нужно отдельно проверять скрипт.
- `departments.path` заполняется цепочкой slug через точку, корневые подразделения получают `depth=0`. В текущей схеме `path` имеет тип `ltree`; применяйте миграции сервиса, которые создают расширения и индексы.
- `deleted_at` не передаётся в SQL и остаётся `NULL`: записи создаются активными.
- Длины случайных названий и адресов и глубина дерева не ограничиваются правилами DirectoryService. Большие наборы могут нарушить ограничения столбцов; уникальность названий локаций проверяется только внутри текущего набора, а не относительно базы.
- Запись напрямую в таблицы обходит инвалидацию кеша DirectoryService. Для проверки новых данных используйте чистое окружение или отдельно обеспечьте сброс его кеша.
- Ошибка `tx.Commit` сейчас не проверяется. Сообщения об успешных отдельных вставках не гарантируют сохранение транзакции; при необходимости проверьте результат запросом к базе.

Тестовых файлов в модуле пока нет. Проверить компиляцию пакетов можно без подключения к базе:

```bash
go test ./...
```
